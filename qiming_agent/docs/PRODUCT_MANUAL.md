# 企明｜产品、运行与结构手册

## 01  一页认识企明
不是再造一个财务软件，而是把已有脚本变成有依据、可核对的经营分析工作台。

项目全名：企明｜照明产业链经营与财报 Agent。面向中小企业经营分析、采购支持人员的个人改造原型。这里的“企业”是预期使用者，公牛等上市公司只是公开产业链观察样本，不是项目客户。

### 一个具体任务

经营会上有人问：“公牛 2024 年收入增长了，经营现金流为什么下降？”企明先给出经核对的收入和现金流，再提示应查阅的报表、口径与附注。没有证据支持原因时，只写“待核实”，不编造回款困难，也不自动调整采购或授信。

|过去的做法|企明增加的能力|
|---|---|
|运行几个 Notebook、找结果表|统一任务入口，明确公司、年度、处理步骤|
|复制数字到分析材料|程序计算并保留报告编号、页码和单位|
|在文件夹里找规则说明|检索当前有效、有权限的知识与来源|
|发现错误后口头沟通|执行记录与分类反馈，提交人工复核待办|

### 业务价值如何验证

现阶段证明的是“流程可以重复运行、数字有来源、边界能被检查”。尚未开展真实企业试点，不能把测试通过率当用户满意度，也没有测出节省多少人力。真实收益应在试点中记录从收到任务到复核完成的总时间、返工次数和材料采用情况。

本手册用“已经实现、可选接入、后续建设”区分状态。新原型为本次 AI 辅助改造成果，不能倒写成过去实习期间的生产成果。

## 02  旧项目如何变成新作品
保留可靠的规则与计算，把 AI 放在解释和交互层，而不是让模型接管财务数字。

|来源|实际基础|本次改造|
|---|---|---|
|三大报表清洗仓库|遍历文件、项目匹配、跨年汇总|年份与路径参数化；数值规范化；重复和缺失检查|
|年报提取仓库|定位 PDF 关键词页、提取表格|限制合并报表范围；保留页码；先产生待审核候选|
|施罗德脚本仓库|数字清洗、可比池、指标与模板输出|统一数据入口、经营简报、可追溯展示；不挪用产品数据|
|文枢参考包|固定问答流程、版本/权限、Skill、Trace|缩为本机 FastAPI + SQLite；保留治理思想|
|照明资料包|年报与历史提取表|筛选四份原生年报，逐页核对关键数字|

### 三个值得面试展开的具体问题

旧脚本把 2018—2023 年写死，换年度需要改代码；遇到多个相似项目直接取第一个，可能混淆口径；某段表头判断写成 if A == “序号” or “产品名称”，后半段恒为真。新版分别用参数、重复候选拒绝、显式表头匹配处理。

### 不是照搬参考材料的全部故事

文枢参考文章描述了较完整的微服务、长期记忆和反馈灰度；本次没有复制这些规模和性能主张。原包缺少可确认的根级授权文件，因此不把完整参考包作为自有代码重新发布；新模块是方法级复用与轻量化重构，来源在 PROVENANCE.md 中说明。

阅读范围：原包文件/语法扫描及核心链路阅读；视频抽取八个关键画面，不是完整音轨转写。GitHub 对利润表、现金流直接法、年报提取、净值对比全文阅读，对数字转换和五只产品对标检查相关片段。

## 03  数据口径与可信度
财务分析的第一步不是生成解释，而是确认“这是谁、哪一年、什么单位、什么口径”。

|报告|本次使用数值年度|定位|
|---|---|---|
|公牛集团 2024 年报|2024、2023|终端电工与照明|
|民爆光电 2024 年报|2024、2023|商用/工业照明|
|兆驰股份 2024 年报|2024、2023|显示与 LED 产业链|
|晶丰明源 2023 年报|2023、2022|电源管理芯片|

每份报告选取 21 项指标、两年数据，共 168 条；均为合并报表，货币为人民币，底层数值单位为元。界面换算亿元仅为展示。来源清单保存原文件名、报告年度、SHA256 与 PDF 页数，每条事实保存物理页码。

### 三种不能混淆的情况

报告年度不等于每列数值年度：2024 年报里也有 2023 年比较数。合并净利润不等于归母净利润：现金流与利润对照使用合并口径，同时展示归母供识别。资产负债表货币资金不必等于现金流量表现金及现金等价物，不能把二者不相等直接报成错误。

### 已执行的检查

资产＝负债＋权益；现金净变动＝经营＋投资＋筹资现金流＋汇率影响；期末现金＝期初现金＋净变动。8 个公司年度组合共有 24 项勾稽检查，本次全部通过。勾稽通过只能证明这些数值关系相容，不能代替审计，也不能证明每一个业务事实准确。

### 缺数据时怎么办

晶丰明源缺 2024 年已核对数据时，返回不足，不借用 2023 年。同比基数为零或负数时不按通常公式展示增长率；合并净利润非正时不展示现金流/利润比。缺失值不是零，调整前/后并存必须先选定口径。

## 04  使用界面与演示路线
先展示一个完整任务，再解释技术。四个页面各自对应一类业务动作。

本地演示工作台：历史财报样本、任务入口与数据边界。（截图见随附 Word 手册）

|页面|看什么|
|---|---|
|经营概览|样本公司、报告年度、关键指标；不混年排名|
|任务工作台|输入问题、处理结果、来源、步骤和反馈|
|知识与版本|编辑提交新版本；另一演示身份审核发布|
|执行与反馈|本人任务记录；编辑处理待复核反馈|

四分钟演示：第一分钟问“公牛2024年现金流分析”；第二分钟展示源值与勾稽，并说明不能直接推出下降原因；第三分钟改问“晶丰2024年现金流”展示缺数；最后展示待审知识不能被引用、自审发布受阻和第二人发布。

## 05  架构：程序、知识与模型分工
最重要的边界：模型可以解释任务，但不能改写账本或绕过审批。

```text
界面 / 命令行
  ↓ 服务器确认身份与可访问部门
Intent：公司、年度、任务识别
  ↓
Rewrite：按 Skill 扩展检索词
  ↓
财务工具：查数 → 勾稽 → 比率/同比 → 简报
  ↓
检索：有效版本 + 权限过滤 → BM25 / 可选语义向量
  ↓
Answer：程序结果 + 可选模型定性草稿
  ↓
Verify：来源存在、权限、版本、哈希与原文片段
  ↓
人工复核 → Trace → 反馈待办
```

|模块|代码入口|控制点|
|---|---|---|
|财务事实与计算|finance.py / data/|Decimal 计算；不让模型算数|
|原文件候选提取|ingest.py|新增数据始终待核验|
|文档与审批|store.py|权限、有效期、第二人、事务切换|
|检索与证据|retrieval.py|检索前过滤；返回前回查|
|外部模型|model.py|显式开关、超时、结构与引用检查|
|流程与接口|engine.py / app.py|白名单 Skill；身份由服务器决定|

默认使用单机 SQLite 和 BM25。配置真实嵌入服务才启用语义向量与 RRF；配置生成模型且用户勾选后才尝试生成定性草稿。当前不是自主规划 Agent，不包含 Milvus、重排模型、长期记忆或 MCP Server。

## 06  Skill 如何真正执行
Skill 是一套可复用的任务做法，不是一段“请认真回答”的提示词。

|Skill|输入|执行与输出|
|---|---|---|
|三表核对|一家公司＋年度|读取事实、三项勾稽、汇总指标及页码|
|利润与现金流|公司＋年度＋现金流问题|比较利润与现金流、检索口径、列待核实事项|
|应收与存货|公司＋年度|展示营运资金相关项目、同比和流动比率|
|产业链样本对照|至少两家公司＋同年度|核对数据可用性、并列展示、不做综合排名|
|经营会议简报|公司＋年度|组织关键数值、程序计算、来源与复核清单|
|知识依据问答|口径或流程问题|检索有权限的有效知识；无证据明确不足|

### 输入同样一句话，实际发生什么

“公牛2024年现金流分析”命中 cashflow。系统识别 603195 与 2024，调用财务快照/简报，并加入“经营现金流、合并净利润、原因、待核实”等检索词，top-k 为 5。Trace 记录 Skill 名称、版本、工具集合、扩展词及最后进入答案的证据。

### 与原有程序的关系

Skill 并不重复写一套财务算法，而是把数字规范化、读表、计算和报告等已有方法组织成固定路径。这样既能复用历史能力，又能让使用者通过业务问题选择任务。

### 反馈会不会自动修改策略

不会。反馈先选择数据、检索、意图、生成或知识缺口类别。编辑只能确认“进入开发待办”或驳回；开发者修改 engine.py 中的 SKILLS 后，还要运行测试、评审再发布。skills 目录是同步的说明文档，不是暗中执行的任意脚本。

## 07  权限、版本与错误处理
出现故障时降低功能，不把不确定的结果包装成确定结论。

|情况|当前行为|
|---|---|
|分析员想写入文档|拒绝；写入需要服务器配置的编辑身份|
|编辑想发布自己提交的版本|拒绝；需要不同 user_id 的编辑复核|
|新版本未审核或未生效|不进入普通问答；旧的有效版本保持可用|
|发布新版本|同一数据库事务归档旧版并激活新版|
|无有效证据|不调用模型补答案；明确需要材料或人工确认|
|嵌入服务失败|标明降级为 BM25，不声称语义检索成功|
|生成服务失败/引用不合法|返回程序结果与原文；不静默替换|
|新报告自动抽取|只产生候选，不自动写入可信账本|

### 校验能保证到什么程度

现在可检查来源 ID、版本、可访问性、正文哈希和引用片段。模型输出限定为带来源的定性草稿，不允许混入阿拉伯数字；但中文数字或定性表达仍可能有误，因此该约束不是完整语义校验。引用存在也不等于结论一定由引用支持，仍须人工复核。

### 与生产系统仍有距离

演示身份不是企业 SSO，角色下拉菜单不是正式身份核验；本机没有公网限流、备份恢复演练或生产审计留存策略。财务种子数据是公开样本，并非多租户私有 ERP 数据。未来接企业数据，应先明确授权、隔离、保留时间与模型外发范围。

不存在自动发邮件、付款、审批、调授信额度或改 ERP 的工具。不要将“能生成草稿”表述成“可以自主执行业务”。

## 08  安装、运行与接入模型
首次使用先跑不依赖模型的演示；确认数据和流程后，再接你有权使用的模型服务。

### Windows PowerShell

```text
cd 解压后的项目目录
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m qiming serve --port 8765
```

### macOS / Linux

```text
cd 解压后的项目目录
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m qiming serve --port 8765
```

浏览器打开 http://127.0.0.1:8765。默认分析员只读 research 部门；editor/reviewer 可演示两个不同账号的发布流程。按 Ctrl+C 停服务。全部包安装仍需要正常的软件包源；本次交付不是附带全部依赖的离线安装盘。

### 模型设置（可选）

```text
$env:QIMING_ALLOW_EXTERNAL="1"
$env:QIMING_MODEL_BASE_URL="https://你的服务地址/v1"
$env:QIMING_MODEL_API_KEY="你的密钥"
$env:QIMING_CHAT_MODEL="你的模型名称"
$env:QIMING_EMBEDDING_MODEL="你的向量模型名称"
```

上述为 PowerShell 示例；macOS/Linux 改用 export。程序不自动读取 .env.example；配置后重启服务。模型名称、接口权限与费用由你的服务商确定，不预填或代付。仅配置嵌入会改变检索，生成还须勾选“模型草稿”或命令行 --model。

本次没有配置真实模型密钥，因此不报告真实 RAG 准确率或云模型延迟。外部调用接口、失效和异常路径用模拟响应做测试。

## 09  新报表接入与后续运营
第一版把可信度放在速度之前：下载和抽取可以自动化，正式入账仍需人工确认。

### 原生 PDF 候选提取

```text
python -m qiming ingest report.pdf --company 603195 \
  --name 公牛集团 --year 2024 --out candidates.json
```

输出会标记 pending_review。核对原 PDF 的合并/母公司、当前/比较年度、调整前/后、单位和页码。当前解析器仅对本次四份原生报告版式进行了验证；扫描 PDF、不规则附表需要其他路径，不会自动做 OCR。

### 旧 Excel 的复用方式

当前轻量版不内置复杂 Excel 引擎，先将目标工作表另存为 UTF-8 CSV，再运行 normalize-csv。旧表的“日期列”和项目名匹配逻辑可以继续利用；重复行会报错而不是取第一条。原文件不覆盖。

```text
python -m qiming normalize-csv report.csv --company 603195 \
  --years 2024 2023 --statement is --unit 元 --out normalized.json
```

### 正式财务数据的发布尚未做成按钮

人工核验后，通过代码评审更新 financial_facts.csv 与 sources.json，运行 check-data 和测试，再创建新本地数据库以重建对应财务知识。旧 workspace 应先备份并改名；不要随意删除真实使用记录。UI 的知识发布只管理说明文档，不能绕过独立核验覆盖财务账本。

### 后续优先级

先做财务候选的双人复核与账本/知识同步发布；再增加原 PDF 可访问链接和更多版式测试；随后进行真实模型评估与业务试点；最后才考虑更多 Agent、任务队列、SSO、并发和自动化订阅。公开下载辅助当前仅对白名单 HTTPS 直链做安全与格式检查，不等于已完成定时财报抓取。

至少运行三个正常问题、一个缺数问题、一次知识新增与自审失败；打开 engine.py 的一个 Skill，顺着调用找到 finance.py 的数值与 retrieval.py 的依据；修改一个失败案例并补测试。只有能解释这些动作，才能把项目写成自己的个人改造经历。
