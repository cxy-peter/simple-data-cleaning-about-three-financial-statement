# 企明｜面试问答与名词手册

## 01  先把项目讲清楚
叙事顺序：真实旧方法 → 当前问题 → 新增功能 → 验证 → 边界。

### 一分钟自述

我做的项目叫企明，是一个面向照明产业链经营分析的财报 Agent 原型。它不是从零替代 Excel，而是在我已有的三大报表清洗和金融产品报表经验上，增加任务入口、知识检索和复核流程。数字由程序读取和计算，知识负责解释口径，模型只作为可选的定性草稿能力。

现在已经把四份历史年报的 168 条关键数值整理成可追溯数据，支持三表核对、现金流、应收存货和经营简报等六类任务，并加入知识版本、第二人发布及执行记录。当前验证是本地测试和固定任务回归，没有真实企业上线，也没有把参考文章的效果数据当作自己的成果。

### 三分钟展开顺序

先用“经营会上需要从多份财报汇总、核对、解释数据”说明场景；再展示旧 Notebook 固定年份、首个匹配行和表头判断的限制；第三步说明为何保留程序计算、增加 RAG 和任务层；第四步走一遍公牛现金流问题；最后展示晶丰缺少 2024 数据时的处理和一个自审发布拦截。

### 这个项目到底是谁做的？
这是基于我过去脚本、提供的参考工程和公开报告进行的 AI 辅助个人改造。参考设计、新写模块和已有实习工作分开记录。我需要对自己提交的代码和解释负责，但不会声称一个人原创了所有技术，也不会虚构学校或企业合作。

### 为什么不继续把 Home Credit 当主项目？
这版简历主要展示 AI 应用产品能力。Home Credit 的竞赛成绩可以留在证书项，但主项目换成更能说明任务定义、系统边界、数据来源和使用流程的作品。更换项目不代表建模经历无效。

## 02  业务场景与产品取舍
说得出为什么做、为谁做、不做什么，比罗列模型名更重要。

### 为什么选择照明产业链，不直接沿用高校行政助手？
因为我已有财报清洗、产品对标和报表自动化的基础，也有可核对的照明公司公开报告。这个场景能把旧工作与新能力连起来，不需要编造学院或网信办委托。目标使用者是小企业的经营/采购支持人员，当前只做原型，不声称已完成用户调研或真实客户验证。

### 旧脚本能处理表，为什么还需要 Agent？
旧脚本解决单个环节，用户仍需要自己选文件、切年份、查口径和整理材料。新任务层把这些动作串起来，同时记录输入和来源。AI 的增量主要在自然语言入口、知识查找和定性草稿；不是声称模型算数比程序快。

### 这些公司规模差异大，能直接比较吗？
不能把它们放成同质排名。它们分处终端电工照明、灯具、显示 LED 和芯片环节。当前只做相同年度的并列观察，并明确可比性边界。真正做同业对标还需要产品结构、地区、业务模式和会计口径筛选。

### 你怎么定义成功？
第一层是正确性：年份、单位、合并口径与来源一致；第二层是任务完成：用户能得到可复核的材料；第三层才是收益：试点中的总处理时间、返工、采用率。当前只有前两层的部分本地验证，不把 73 项单测解释为节省人力或满意度。

### 第一版为什么不做付款或 ERP 写入？
因为读数和生成草稿容易检查、可撤回，而付款、修改额度会产生真实业务后果。先把事实、权限、错误处理做好，再谈经授权的写操作。这也是资源有限时的范围控制。

## 03  RAG 与数值：不能混为一谈
检索找依据，计算走工具。存在引用只是最低门槛。

### RAG 在这个项目里具体做什么？
它检索财务口径说明、业务方法和当前有权限的知识，把证据交给可选生成模型。报表金额、比率和同比不靠语言模型生成，而由 Finance 工具读取和计算。默认没有模型时只返回原文摘录和程序报告。

### 默认模式真的用了向量检索吗？
没有。默认是 BM25，中文使用双字片段做确定性分词。只有显式配置嵌入服务才计算向量、余弦相似度，并与 BM25 用 RRF 融合。本次对接口用模拟响应测试，没有真实嵌入质量结果。

### 为什么不能让模型自己从 PDF 把数字都读出来？
可以让模型辅助提出候选，但金额还涉及列、单位、年度、合并/母公司、调整前/后。同一标题可能在多个章节出现。当前候选提取后必须人工对原 PDF 核验，正式结果才进入财务种子账本。没有把任意 PDF 自动解析当作已解决问题。

### 怎么避免编造来源？
返回前回查有效文档、权限、版本哈希和逐字片段；模型引用 ID 必须来自本次证据。无证据不调用生成。结构检查仍不能判断所有定性结论是否被支持，所以模型段落明确标为待人工语义复核。

### 为什么不用 Reranker、Milvus 或更复杂的记忆？
当前只有小规模知识和四份报告，先验证业务流更有价值。内存 BM25、可选向量缓存和 SQLite 足以演示。没有做重排和长期记忆就直接说明，不能为了面试把参考包全部技术栈搬上简历。

## 04  Skill、执行与反馈
不要把受限 Workflow 说成模型可以自主改变系统。

### 一次任务有哪些步骤？
先确认身份，再识别公司、年度和任务。选定 Skill 后扩展检索词，调用白名单财务工具；接着检索当前有效的授权知识，组织程序结果和可选模型草稿，校验来源后记录 Trace。缺公司或年度先澄清，不默认为最新。

### Skill 怎么证明不是装饰？
看 engine.py 的 SKILLS：现金流与应收存货任务使用不同关键词、top-k 和报告内容；对照任务必须有至少两家公司和同一年。Trace 显示命中哪项 Skill、版本、工具集合和证据。技能说明文件用于解释，真正执行的配置在代码中。

### 为什么固定流程，不用全自主 ReAct？
任务形态相对稳定，先查数再找依据，不能允许跳过这些环节。规则式路由容易测试和解释，但灵活度有限。这是当前产品取舍，不代表固定 DAG 比 ReAct 在所有场景更好。

### 用了 MCP 吗？
当前没有实现 MCP Server。内部工具由 Python 直接调用。MCP 是标准连接协议，Skill 是任务策略包；二者不是同一个概念。未来需要多个客户端共享工具时再加协议适配，不把普通函数调用写成已经完成 MCP 接入。

### 用户点踩后系统会自动变聪明吗？
不会。反馈按数据、检索、意图、生成或知识缺口分类进入待办。复核只决定是否进入开发；代码修改、测试与评审之后才发布。现在是可追踪的人在环迭代，不是自动灰度或自进化训练。

## 05  失败、权限与验证追问
把正常演示之外的限制讲清楚，项目才经得起深挖。

### 新版本发布失败时旧版怎么办？
当前知识都在同一 SQLite 中，归档旧版和激活新版放在一个事务里，失败回滚。只有不同于提交人的编辑才能发布，且要检查生效期和版本号。这不能推广成已解决 Mongo 与向量库的分布式事务。

### 怎么防止用户在请求里冒充管理员？
身份和可访问部门来自服务端 token 配置，而不是由问题文本或前端角色字段决定。默认演示 token 是公开的，只可本机使用；生产还需要可信登录、密钥轮换、审计与限流，当前不声称企业级安全。

### 模型不可用还有价值吗？
有。数据读取、勾稽、比率、简报和 BM25 原文检索仍能工作。语义检索依赖查询向量服务，服务失败要回退关键词；不能因为文档向量已缓存，就说新问题不需要嵌入。

### 你报告的测试结果是什么？
73 项程序测试和 12 个固定业务回归通过；168 条财务数值核对；24 项勾稽通过。模型与下载路径用 MockTransport，浏览器因环境网络限制使用 fetch 桥接到本机 API。没有真实用户研究、模型准确率、并发压测或稳定节省工时的结论。

### 接下来最先改什么？
优先把新财报候选审核、财务账本和知识索引更新做成一致的发布流程；之后扩充版式、补真实模型评估和少量用户试点。先解决数据正确性和可用性，再加更复杂的 Agent 编排。

## 06  名词速查：业务人员也能理解
每个词都对应本项目中的实际动作；没做的部分明确写出。

|名词|通俗解释|企明中的对应|
|---|---|---|
|Agent|围绕目标选择或执行工具的助手|受限工作流型，不是全自主规划|
|Workflow / DAG|按规定顺序经过的工序|识别、工具、检索、回答、校验|
|Harness|约束流程和工具的外层控制|白名单、权限、停止条件、记录|
|RAG|先找资料，再基于资料回答|默认原文检索；生成需配置模型|
|Embedding|把文本表示成可比较的向量|可选真实服务；本次未实调用|
|BM25|按关键词相关性找资料|默认可运行的检索方式|
|RRF|综合几路检索名次|可选语义与关键词融合|
|Reranker|对少量候选再精细排序|未实现，不写成已使用|
|Skill|可复用的一套任务步骤|六类任务工具、词和参数|
|MCP|不同 AI 应用接工具的标准接口|当前未实现 Server|
|Trace|这次任务做过什么的流水记录|输入、任务、证据、结果与模式|
|Schema|输入输出应有的字段与格式|API 参数与模型输出检查|
|事实库|最后以哪份记录为准|已核对 CSV、有效知识与来源|
|ACL / 租户|谁能看哪一组资料|服务端身份、部门/tenant过滤|

这些名词解释用于理解，不代表系统具备所有同名商业产品的功能。对非技术面试官可以先说“流程控制、带来源查询、任务包、执行记录”，需要时再补英文名称。

## 07  指标与财务术语速查
正确解释分母、单位和范围，比背一个漂亮指标更重要。

|概念|怎样理解|常见误区|
|---|---|---|
|合并 / 母公司|整个集团与母公司单体不同|混用两套收入或资产|
|合并净利润 / 归母|总体利润与归属母公司股东的部分不同|与合并现金流随意交叉使用|
|元 / 万元 / 亿元|同一金额的不同显示尺度|单位错位产生一万倍误差|
|同比|与上年同一期间对照|负基数照常算“增长”|
|勾稽|几项数字之间应满足的关系|把等式平衡等同审计通过|
|Recall@k|前k条找回相关资料的比例|和命中至少一条混淆|
|Hit Rate@k|有至少一条相关结果的问题占比|误写成召回率|
|MRR|第一个相关结果排名倒数的平均|不说明相关性的标注方式|
|引用正确率|结论和来源确实对应的比例|只检查有引用符号|
|单元测试|对指定逻辑和异常的程序检查|说成用户准确率或满意度|
|回归测试|改动后原先正确场景是否仍正确|只展示正常新功能|
|P95|95%请求不超过的耗时|单次演示耗时充当P95|
|灰度|先让一小部分流量试新版本|本项目反馈待办不是灰度系统|
|OCR|从扫描图片识别文字|原生PDF读文字不叫OCR|

### 一句话收尾

我希望通过这个项目证明：我能把已有自动化能力组织成业务可使用的产品流程，知道哪些交给程序、哪些交给模型、哪些必须交给人，而不是只把技术名词堆到一个聊天页面上。
